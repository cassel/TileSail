## Confirmed new finding and remediation

**P2 — oversized server responses can leave the CLI waiting indefinitely.**
The prior framing correction made `NWConnection.writeAtomic` reject messages
larger than 16 MiB before sending any bytes. `server.swift` discarded its error
and proceeded to wait for another request, while `Cli/_main.swift` waited for the
response. A supported query with expanded output can exceed the limit even when
its request is below the cap. The Swift and security reviewers independently
identified this deterministic integration failure.

`Sources/AppBundle/server.swift:37` now routes responses through
`sendServerAnswer(_:over:)`. EMSGSIZE generates a small decodable `ServerAnswer`
with exit code 2, empty stdout, and guidance to reduce the output. Other write
failures, or a failed fallback write, cancel the connection. The normal response
path calls the helper at line 59.

`SocketFramingTest.testOversizeServerAnswerReportsErrorAndPreservesConnectionFraming`
uses actual private temporary sockets, verifies the error arrives promptly, and
then verifies a normal response on the same connection. Existing header/body,
fragmentation, EOF and writer-bound tests remain intact.

## Residual concerns and review limits

1. **Pre-existing IPC trust boundary:** predictable `/tmp` socket pathname with no
   explicit application peer-identity check. Different-UID access was not tested.
   The local `unix(4)` manual describes socket write-permission checks, so mode
   bits alone must not be presented as proof that another user can connect.
   Owner-private endpoint storage and peer enforcement remain design/validation
   work; see [SECURITY.md](../../SECURITY.md).
2. **Pre-existing parser depth candidate, not reproduced:**
   `Sources/AppBundle/shell/shellParser.swift:77–80` recursively parses grouped
   expressions without an explicit nesting cap. `EvalCommand.swift:8` reaches
   this parser through `eval`; the frame limit is not a recursion-depth limit.
   Possible stack exhaustion is a static-review candidate, not a measured crash.
   A safe defensive nesting limit and its boundary tests are follow-up work.
3. **Blocked reproduction:** an automated safeguard blocked the requested isolated
   stack-exhaustion reproduction as a possible cybersecurity risk. It was not
   retried. The security reviewer subsequently completed source-only defensive
   review, without a crash harness, payload generation, account changes, or
   contact with the running application's socket.
4. Existing startup migration, actual Stream Deck focus, display reconnect/wake,
   Release packaging/signing/notarization, and cross-user acceptance work from
   the first audit remain outside the established runtime evidence here.
